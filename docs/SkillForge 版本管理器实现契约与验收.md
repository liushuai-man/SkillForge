# SkillForge 版本管理器 · 实现契约与验收

> 版本：v0.1，2026-10-08。本文规定后续实现的交接边界与验收证据，**不是当前实现能力清单**。
> 产品范围、需求与设计取舍以[设计文档](./SkillForge%20版本管理器设计文档.md)为准；排期见[分工与交付计划](./SkillForge%20版本管理器分工与交付计划.md)。本文不另设第二套产品需求。
> “已定”表示可以据此实现；“待决”表示相关任务不能靠猜测开工。本文新增要求不会自动改变已有数据格式或迁移数据库。

## 1. 模块交接与单一真值

### 1.1 数据归属

| 数据 / 能力 | 维护方 | 消费方式 |
| --- | --- | --- |
| 工作区配置、路径与忽略规则 | A / M-01 | 读取不可变的有效配置快照；其他模块不重写 workspace.json |
| 对象编码、读写、完整性 | A / M-03 | 通过对象库公开接口读取原始 bytes；消费者不自行拼存储路径 |
| Revision、Change、Ref、路径索引 | A / M-04 | 解析引用、获取修订、列历史；M-05 不直查 revision/ref 表 |
| Op 与操作前后状态 | A / M-09 | 业务提交入口组织事务；路由与 CLI 不拼 SQL |
| 文件差异与分层缓存 | B / M-05 | 以不可变 Revision 对和固定分析配置为输入 |
| 结构解析、语义单元 | B / M-06 | 接收内容/路径/配置并返回纯数据；不读数据库、不自行访问 Skill 根 |
| 聚类 | B / M-07 | 接收变更单元；保留其 ID 与证据，不重读文件 |
| 规范报告与报告存储 | B / M-08 | 接收 M-05 结果，组装规范报告；不自行解析或读取对象库 |
| HTTP / CLI / UI | A / M-10、M-12；B / M-11 | HTTP 是共同入口；UI/CLI 不重新实现 diff、ref 解析或结论规则 |
| SQLite 连接与物理 DDL | A / db | 提供连接/事务基础；表内操作由对应模块封装，不能变成任意模块的 SQL 通道 |

不得为每个调用再建一套近似 DTO。公共 Pydantic 模型放在数据拥有模块的公开模型文件；通用 ID/枚举可放 core。`__init__.py` 存在不等于公开接口已实现。

### 1.2 两线交接最小包

跨模块实现开始前，提供并由消费方核对以下内容（可放在任务描述/PR，不强制新建文档）：

1. 一个公开入口及其输入/输出模型，字段类型、必填/可空、默认值、枚举与排序规则。
2. 一组正常、空结果、失败/降级样例，使用同一份 schema 校验；示意图中的缩写 ID 不可用作真实测试 ID。
3. 该调用会修改什么状态，事务/提交边界是什么；失败后能否重试、有何幂等性。
4. 提供方与消费方共用的契约用例。假数据必须符合此模型，不得先各写一套字段再联调。

仅内部重构且公开行为不变时，不重复走协议确认。对象格式、DDL、错误码、公共字段、状态语义变化必须先更新权威章节，给出兼容影响；不能靠前端临时兼容字段名掩盖分歧。

## 2. 状态与提交边界

### 2.1 工作区初始化

- 准备中的工作区不出现在正常列表。所有对象、数据库与配置完成后才发布可见标志；发布失败也属于初始化失败。
- 失败清理只处理本次创建、位于独立数据根内的临时产物，绝不能删除 Skill 文件或其他有效工作区。也可保留可识别的中断产物供恢复，但再次 init 必须能安全重试。
- 同一路径重复成功 init 报 `workspace_already_initialized`；先前失败不应占住该路径。单个损坏工作区给出明确诊断，不应让其他有效工作区无法列出。
- 规范路径按实际平台大小写规则比较；拒绝数据路径等于或位于 Skill 根内。内部扫描路径使用根内相对路径；拒绝越界、绝对路径和 `..`，不跟随符号链接/junction。

### 2.2 快照、引用与操作

| 情况 | 必须发生 | 不能发生 |
| --- | --- | --- |
| 仅 mtime 变化，tree 与当前相同 | 返回当前 Revision，created=false | 新对象、新 Revision、Op、seq、元数据时间戳写入 |
| 原始内容/路径改变 | 先写对象，再同事务提交索引、Revision、Change、状态/Op，created=true | 数据库提交前发布成功事件 |
| A→B→A | 第三步创建新 Revision，复用 A 的 blob/tree | 跳回旧 Revision 并抹掉这次变化事件 |
| 无锚点 | 默认比较 base=null 与捕获到的 head | 自动创建 stable 或空 Revision 数据行 |
| 用户打锚点 | 先取得当前稳定 Revision，再同事务移动 ref 与选中 Baseline、记录 Op | 保存文件时自动推进用户 Baseline |
| 引用在计算中移动 | 本次报告仍使用入队时固定的 Revision 对 | 一个报告混用新旧基线 |
| 数据库提交失败 | 不公布新状态；允许留下未引用对象供重试 | 清理已经被其他已提交历史引用的对象 |
| 进程强杀后重启 | 识别未发布初始化/临时对象，重扫工作区，保持已提交状态 | 把“有对象文件”当作“快照已提交” |

`@` 的捕获和锚点操作复用同一个串行快照入口。并行对比只读已提交内容。业务事务不得嵌套各自 commit；SQLite 外键约束不会自动补足文件系统一致性。无变化“零写入”指对象与业务元数据，诊断日志单列测量；不能用日志写入伪装成 Revision 更新。

监听只产生提示：启动时先做一次全量扫描兜底（补上服务停止/监听未就绪期间的变化），此后每次事件触发同样走全量扫描与稳定校验；无变化时该次扫描为零写入。因此「未捕捉到事件」不会导致最终稳定状态漏记（AC-05）。

### 2.3 撤销：明确待决边界

**TBD-08 已关闭（2026-10-13 用户明确批准）**：仅显式预览并确认的整个 Skill 恢复与撤销最近恢复允许文件回写，自动纳管仍只读。恢复 v1 以 §2.4 为准；以下早期 TBD-09 草案保留作来源说明，恢复部分已被 §2.4 冻结定义取代。

**TBD-09 已关闭（2026-10-15 A/B 核对）**：Baseline 采用保留引用 `baseline`；成功创建任意显式命名锚点时，命名引用与 `baseline` 必须在同一事务中指向同一 Revision，首次锚点前以 `base.rev=null` 表示空树，旧工作区不从已有 ref 推断。当前 Revision/Op 从已提交记录派生；活动 Change 为进程内分组，服务重启后新开。唯一状态语义如下，理由见 ADR-0001/0003：

| 状态 | 必须回答的问题 |
| --- | --- |
| 当前已提交 Revision | 与 last（最大 seq）及物理文件状态是否相同；撤销后如何显示/重新扫描 |
| 当前 Baseline | 保存选中的 ref 名还是固定 Revision；同名 ref 更新/撤销后如何解析 |
| 活动 Change | 空闲、打标、重启、撤销边界如何一致判断；不制造空 Change |
| 当前 Op | 撤销针对哪个操作；自动快照是否是撤销目标；如何区分补偿与删除历史 |
| Op payload | 各 kind 的必填 before/after、引用内容及格式版本；重试与重复提交如何处理 |

若需要 DDL 变化，先按 AGENTS 的兼容流程决定，再改 schema，不能往 config_json 临时塞未约定状态。以上待决项不阻塞对象库、纯 diff 与语义样例，但**会阻塞完整“可撤销”验收**。不能仅删除待决标记而没有决策内容。

**第 2 周已有实现基础**：

- **当前已提交 Revision**：由已提交的 `revision` 表按 `ws_id` 取最大 `seq` 派生，不新增状态载体；`last` 只读别名与它同源（设计 §7.2、§7.4）。
- **活动 Change**：无独立载体。分组由「本进程内上次提交时刻 + 单调时钟」派生，空闲满 30 分钟、打锚点或撤销后结束，服务重启自然开启新 Change（设计 §7.2）。
- **Baseline / 当前 Op**：Baseline 使用保留引用 `baseline`；当前 Op 取工作区最新已提交 Op。各 `kind` 的 before/after payload 继续使用本节已冻结格式及 §2.4 恢复格式。

**第 3 周状态契约（2026-10-15 经 B 核对）**：

- **当前已提交 Revision**：派生，取该工作区 `seq` 最大的 `revision` 行（与 `last` 同源）；无新增载体。
- **活动 Change**：仍为进程内派生（单调时钟 + 30 分钟空闲）；服务重启开启新 Change，不回溯。
- **当前 Op**：派生，取 `op` 表该工作区 `rowid` 最大的行；无独立指针载体。
- **Op 载荷格式 `v=1`**：规范 JSON（`canonical_json`，键排序、紧凑、非 ASCII 不转义），固定含 `v`。各 `kind`：
  - `workspace.init`：`{v, revision_id, root_tree_oid, file_count}`。
  - `snapshot`：`{v, revision_id, parent_rev_id, seq, trigger, message}`（`message` 可空）。
  - `ref.set`：`{v, name, before_rev_id, after_rev_id}`（`before_rev_id` 首次为 `null`）。
- **写入边界**：`op` 行在对应业务事务内插入（与 Revision/Change 同一事务）；无变化快照不写 `op`；提交失败随事务回滚，不留半条记录。
- **Baseline 已冻结**：保留 `ref` 名 `baseline` 为唯一选择载体；任意显式命名锚点成功创建时与该命名引用同事务更新。恢复操作不移动任何 ref；旧工作区不从已有 ref 推断。重启后活动 Change 不回填。恢复语义以 §2.4 为准。决策理由见 ADR-0001/0003。

### 2.4 受控文件恢复 v1（2026-10-13 用户批准，覆盖 §2.3 中恢复待决描述）

TBD-08 已关闭：自动纳管仍不写 Skill；用户明确发起、预览文件清单并确认后，允许恢复整个 Skill 到指定 Revision，及撤销最近一次文件恢复。逐文件恢复、部分变更恢复、任意历史 Op 跳转和撤销打锚点暂不实现。TBD-09 已按 ADR-0001/0003 关闭；本次恢复不移动任何 ref。是否达到完整 G2 仍取决于默认报告、UI 与跨线真实流程验收。

- 预览先捕获当前稳定内容作为 before Revision，再固定目标 Revision；返回新增/修改/删除文件、目录清单和 plan_id。目标与当前相同返回无变化，不创建恢复操作。预览本身不回写 Skill。
- 用户确认必须携带 plan_id；CLI 每次展示清单后交互确认（自动化须显式 --yes），API 必须 confirm=true。旧计划遇到新的已提交修订、配置或磁盘变化即冲突，不覆盖。未保存的编辑器缓冲区不在服务保护范围内。
- 唯一持久化载体为现有 op 表（无 DDL/对象格式变化）。新增三种 kind，payload 保持 v=1：restore.plan 保存 before_rev、target_rev、action（restore/undo_restore）、配置指纹、根身份与按路径排序的影响清单；restore.begin 保存 plan_id；restore.done 保存 plan_id、before_rev、target_rev、after_rev、action。parent_op_id 指向对应 plan；一个 begin 无 done 即 pending。旧数据无此类记录时视为没有恢复；旧二进制不识别 pending，存在未完成恢复时禁止降级运行。
- begin 必须在首次文件写入前提交。执行共用服务串行写通道；普通快照在 pending 时明确报 restore_pending，不能把半恢复文件提交。仅确认的恢复执行器可在验证最终 tree 等于目标后调用内部完成入口，将新 Revision/快照 Op/restore.done 同事务提交；成功后才通知。历史不删除，seq 继续递增，恢复开启新 Change，ref 不动。
- 使用逐文件同目录临时文件和原子替换，不声称跨文件原子。临时文件名称绑定计划，恢复中断时保留 pending，status 返回计划 ID；用户通过 restore --resume PLAN 再次预览确认后继续。仅接受路径内容仍为计划 before/target 两种状态（临时文件必须是目标字节的前缀）；其他内容、根身份/路径类型/内容冲突、忽略规则变化均停止，不自动回滚或覆盖新编辑。重复执行已完成 plan 返回既有 after_rev，不重复写文件或操作。
- 仅普通纳管文件/目录可写；路径必须在原工作区内，不跟随符号链接/reparse point，拒绝大小写冲突、不安全路径和不受支持的类型。目标涉及当前忽略路径、未纳管文件冲突、需删除含受保护内容的目录时先拒绝。删除仅针对计划中的文件和空目录，绝不递归删除。保留原始 bytes 和受支持的可执行模式。每次写入前与结束时复核；用户应暂停外部编辑，不承诺操作系统未提供的跨进程文件事务。
- undo 以最近 restore.done 的 before_rev 为目标。若该恢复之后已有内容修订，拒绝盲目撤销并提示显式选择历史修订恢复；撤销自身也是恢复，故可再次 undo 撤销这次恢复。
- 新增接口：POST /workspaces/{ws}/restore/preview（rev），POST /workspaces/{ws}/undo/preview，GET /workspaces/{ws}/restore/plans/{plan}，POST /workspaces/{ws}/restore/plans/{plan}/apply（confirm）。沿用统一外壳；restore_conflict/restore_pending 为 409，restore_plan_not_found 为 404。当前 status 增加 pending_restore（plan_id 或 null）。
- AC-18 本轮验收：预览零文件写入；取消不回写；恢复文件新增/删除/修改及空目录；保留当前未捕获内容；undo→undo；ref 不移动；过期计划/忽略文件/链接冲突；失败与重启保持 pending；确认重试恢复并只提交一次；完成后的重复 apply 幂等。单测只使用临时 Skill，不在真实用户目录执行恢复。核心已有 12 项测试，包括 partial/before_commit/after_commit 三处真实进程强杀；文件与目录类型转换、大小写冲突和 Windows 可执行模式变更首版明确拒绝，不能静默部分成功。

- API/CLI 接入验收：API 仅接受布尔 confirm=true；false、缺失、字符串或数字均 422。预览响应为 no_change/plan_id/changes；有变化时附 before_rev/target_rev/action，无变化不创建计划。apply 返回 plan_id/created/revision；created=false 表示此前已完成、本次无回写，不代表当前磁盘仍处于该历史状态。pending 时显式指定修订的打锚点也拒绝。CLI 取消不调用 apply；status 给出续作命令。

- 恢复路径补充验收：历史 tree 非法 Windows 名称与控制字符在预检拒绝；临时文件写入中断后可续作，被其他内容改写则保留并拒绝；文件/目录转换及仅大小写改名拒绝。符号链接冲突用真实链接测试，环境不允许创建链接时明确跳过，不能记作通过。v1 每步全量复核的批量恢复性能尚未验收。

## 3. 对比输入、证据与报告

### 3.1 不可变输入与可复现身份

- 比较输入：`base_rev: str|null`、`head_rev: str`、`layer: L0|L1|L2|L3`、有效 `algo_version`。base=null 唯一表示空树，head 必须是已提交 Revision，且双方属于同一工作区。
- 默认 layer=L3。每项任务开始时固定解析映射、规则/模板/噪声配置，不在处理中再次读取可变配置文件。
- `algo_version` 包含算法、规则、解析器/语法库、报告 schema 版本和有效分析配置指纹；影响结果的配置不能遗漏。数据目录、端口、日志级别等不影响结果的配置不入指纹。
- `report_id = "RPT-" + SHA256(canonical_json([base_rev, head_rev, layer, algo_version]))`。canonical_json 的字节规则与设计 §7.7 相同。
- 位置指向原始 blob，不指向规范化后的字符串。后续开发前用 BOM、CRLF、中文及 emoji 固定样例验证索引映射。

### 3.2 语义变更最小交换结构

| 字段 | 类型 / 规则 |
| --- | --- |
| id | 稳定字符串；由 path/kind/op/两侧位置与内容的规范编码确定派生，不用随机 UUID |
| path | 主展示路径，根内相对路径，统一 `/`；移动时取 after.path，否则取存在一侧 |
| kind | 设计 §3.2 的八类枚举；不得让 UI 自增第九类 |
| op | `add|delete|modify|move`；模糊匹配不凭低置信度直接定为 move |
| before / after | 各为 null 或 SourceSpan；新增 before=null，删除 after=null，修改/移动两侧均有值 |
| rule_id | 判定规则的稳定版本标识，用于追溯；不能将提示词标签当规则依据 |

每个语义单元只有一个主 `kind` 且在规范报告中只出现一次。内容规范编码一致且仅位置变化时为 `move`；内容与位置同时变化时为 `modify`，允许 before/after 使用不同路径；证据不足时保留 add/delete 并进入 `needs_review`。每个单元至多属于一个主 cluster，次级安全/兼容性影响使用风险标签表达。理由见 ADR-0004。

SourceSpan 固定为 `{path, start_byte, end_byte, text}`，偏移从 0 开始，区间为 `[start_byte,end_byte)`，基于原始 UTF-8 字节。text 与该区间解码一致；语义 span 不包含文件首 BOM，但偏移仍从含 BOM 的原始 blob 起算（首字符从字节 3 开始）。展示行号/列号由 UI 从源文本转换，不把 tree-sitter 字节列误当 JavaScript UTF-16 列。

非 UTF-8/二进制文件不强行 replacement decode 后给出语义结论，止于 L0 并说明原因。重命名时两侧 SourceSpan 可以是不同路径；先实现同内容一对一移动检测，歧义候选保留原始新增/删除证据并标待确认。相似度阈值和匹配决胜规则随 algo_version 与固定样例一起冻结，不可藏在 UI。

### 3.3 报告正文

- 顶层：`schema_version, report_id, algo_version, layer, base, head, overview, clusters, layers, needs_review, degraded, behavior`，形状见设计 §4.5。
- `base.rev=null` 表示零基线；ref 名、请求 ID、生成时刻和耗时不进入正文。`head.change_id` 来自不可变修订元数据。
- layers 固定含 metadata/structure/text/semantic；每层 status 为 `not_requested|computed|degraded`。computed+空列表才表示该层已计算且无差异；较低层请求不得伪造 semantic.computed。
- metadata.files 保留各变化文件及 `add|delete|modify|move` 类型；文本 hunks/结构 nodes 的扩展 schema 在相应层开工前由 B 给出合法样例并让 UI 校验，不得让两个消费者各自定义坐标。
- 语义层 units 使用 §3.2；clusters.units 的每个 ID 和 needs_review.unit 的非空 ID 必须能解析到实际单元。无法归类的疑点可用 `{unit:null,path,reason_code}` 表达，不虚构单元。
- degraded 使用稳定 `{path,requested_layer,available_layer,reason_code}`。非文本/超过上限止于 L0，解析失败降到 L1；因一个文件降级不能跳过其他文件。
- overview.files 按变化文件去重；overview.changes 计聚类前语义变更数（未计算时为 null）；overview.clusters 等于 clusters 长度。risk 只能来自有版本的规则映射，不用随机置信度或模型猜值；枚举为 `high|medium|low|unknown`。存在已确认 high 时汇总为 high；否则关键证据不完整为 unknown；否则依次取 medium、low。风险只作提示，不阻断任何操作。
- 风险规则在 L3 单元差异形成后、聚类和报告结论生成前执行；未请求 L3、关键文件降级或关键待确认项产生 unknown。每个风险项必须关联稳定 rule_id、语义单元（如有）、两侧 SourceSpan 和模板原因。
- JSON 字段/枚举/rule_id 使用英文；证据保持源文件原文；MVP Web/CLI 展示与模板结论默认中文。规则覆盖常见中英文表达，无法可靠识别的其他语言按文件降级或待确认。
- 列表按相对路径 UTF-8、类型、位置、ID 排序，所有并列情况有稳定决胜。模板、规则和序列化变化必须更新有效算法版本。
- behavior 在 MVP 固定为 null，界面明确“未接入行为对比”；不要注册成功的占位执行接口。

MVP Web 首屏按“模板结论 → 概览（含各风险等级数与待确认数）→ 按修改目的分组的变化”呈现；风险和待确认直接标在对应变化上。原文、文本和结构证据默认收起并可展开，不提供独立结构视图或专门待确认面板。待确认是报告的不确定性标记；MVP 不提供人工确认/处理动作，不保存 resolved 状态，也不因此引入用户身份或审核工作流。该展示顺序不改变规范报告 JSON 的稳定字段。

MVP 历史页使用稳定分页列表，显示版本时间、触发原因、锚点名称（如有）与简短摘要；每项提供“与当前版本比较”，并允许勾选任意两个版本进行比较。图形时间线、搜索、筛选和版本关系图不在本轮范围。

样例 JSON、Pydantic 验证、TypeScript 消费样例必须交叉校验字段/空值/枚举。文档中的说明性骨架不代替可执行 schema，也不允许照抄不存在的 uXX 引用。

## 4. HTTP、错误与事件

### 4.1 返回与默认值

- 路由前缀 `/api`；默认只监听 loopback。CLI 的 start 是启动服务入口，其他业务命令只调用服务；服务未启动时给出启动提示，不能偷偷直读数据库。
- 成功：`{ok:true,data:...,error:null,request_id:"..."}`；失败：`{ok:false,data:null,error:{code,message,detail},request_id:"..."}`。detail 为 string|null，message 解释具体问题。
- 请求字段验证错误也使用统一外壳；不得泄漏框架默认的另一套错误 JSON。真实未知异常不假冒 object_not_found 等已知原因；以 request_id 关联本地日志，明确说明失败操作。
- diff 的 base/head 省略才使用默认基线/@；显式空字符串、未知引用、错误 layer 报参数/引用错误，不能默默回退。状态接口明确区分处理中、就绪、降级、失败；旧报告只能带明确的旧 head 标记展示。
- MVP diff 为同步 GET：命中缓存直接返回，否则在请求内完成计算并持久化规范报告后返回；`diff/ready` 只在报告已持久化后发布。MVP 不引入任务 ID、后台队列或轮询接口。若存在 Pending Changes，GET 不触发写入，调用方等待 `snapshot/created` 后以新的已提交 head 重试。
- Web 页面处于打开状态时，客户端在首次进入及收到更新后的 `snapshot/created` 时自动请求默认 diff；页面关闭时服务不为界面预先计算报告，下次进入再请求。该流程不设置“开始比较”作为查看最新默认报告的必经操作。
- 自动请求进行期间可保留上一份成功报告，但必须同时显示“旧结果·正在更新”及该报告对应的固定 head；新报告成功后才替换。请求失败时保留旧结果并展示本次失败状态/原因，不能清空成无变化，也不能去掉旧结果标记。
- 列表按稳定 seq/ID 使用游标；请求处理期间固定上界，不能因后续保存导致一页内顺序漂移。
- 每个 POST 在实现前声明重试语义。MVP 不承诺所有 POST 幂等；连接中断后先查询状态核对结果，客户端不得盲目重发 undo。

### 4.2 错误分类

下列错误码多数已在 `src/skillforge_vm/core/errors.py` 定义业务错误类型；`invalid_request / ref_not_found / revision_not_found / snapshot_unstable` 于第 2 周随 M-02/M-04 落地，第 3 周 M-10 已把全部已登记错误码接入统一外壳（含请求校验错误收敛为 `invalid_request`、未归类异常收敛为 `operation_failed`）。未实现路由相关的错误码仍不会被触发，但映射已就绪；`workspace_busy` 的错误类型与 409 映射已定义，Week 4 数据根独占锁已接入服务生命周期，冲突时启动失败并给出该原因（见 §6）。新增错误码必须在此登记并与消费方对齐。

| code | HTTP | 意义 / 处理 |
| --- | --- | --- |
| invalid_skill_root | 400 | 路径无效、不是目录或不满足纳管边界 |
| workspace_already_initialized | 409 | 已有成功初始化；返回已有工作区信息可供定位 |
| workspace_not_found | 404 | 工作区标识不存在 |
| workspace_data_missing | 409 | 已登记工作区的数据缺失/不完整，需要恢复 |
| object_store_not_writable | 507 | 对象存储不可写，停止提交并给出本地具体原因 |
| object_not_found | 409 | 有效历史引用的对象缺失，不能完成对比 |
| object_corrupted | 409 | 解压、头部、长度或 SHA-256 不匹配；停止本次报告 |
| invalid_request | 422 | 参数类型、枚举、OID 语法或区间无效（含框架校验错误） |
| ref_not_found / revision_not_found | 404 | 显式引用或修订不存在；不得替换成零基线 |
| snapshot_unstable | 409 | 工作区持续变化导致本次无法捕获稳定内容，可重试 |
| workspace_busy | 409 | 工作区/数据根已被另一服务写入，不启动第二写通道（映射就绪，触发待接线） |
| operation_failed | 500 | 未归类异常；说明失败步骤与日志 request_id，不编造底层原因 |

`parse_failed / unsupported_encoding / text_limit_exceeded / unsupported_file_type` 是诊断 reason_code，不是整个 HTTP 请求失败码。只有内容不受支持/语法问题可降级；权限拒绝、磁盘满、对象缺失/损坏必须作为失败处理。

### 4.3 事件

- 事件只在相应状态提交后发出。最低数据为 workspace_id 加 revision_id 或 report_id；消费者随后查询权威状态/报告。
- `snapshot/created` 指已提交 Revision；`diff/ready` 指完整规范报告已可取（可包含明确的逐文件降级）；`parse/degraded` 是补充通知。
- SSE 不保证历史重放或恰好一次；客户端断线重连、收到重复或乱序通知后，以 Revision seq 和当前请求身份判定，不让旧报告覆盖新报告。
- API 请求的 request_id、事件传输 ID 与 report_id 不混用；运行时通知时间不进入规范报告正文。

### 5.1 语义质量样例口径

- AC-07/10 JSON 回归补充：`role` 从 writer 改 reviewer 必须产生 role.modify；嵌套示例中的 tools 不单独抽成工具要求；BOM/中文/emoji 的 span 必须逐字节回指原文；排版不改规范值，workflow 数组调序必须改变规范值。对应 `tests/test_semantics.py` 与 `tests/test_diff_report.py`，不修改原有冻结样例。

- AC-10/11 回归补充：重复相同约束后仅追加空行，语义 units 必须为空且不产生虚假 medium 风险；有效 JSON 清空、空 JSON 修成有效内容时，实际存在的任一侧无法解析均按该文件降至 L1，文字证据仍保留且总风险为 unknown。样例追加到 `tests/test_diff_report.py`，算法版本变化不得复用旧错误结果。

- B 在算法实现前先提交冻结的合成基准集，覆盖八类单元的增删改移、否定词、workflow/数组顺序、示例与正文边界、CRLF/BOM/中文/emoji/Markdown 硬换行、坏 YAML、非 UTF-8、2 MiB 上限、模糊移动与纯格式变化。后续可追加脱敏真实 Skill 样例，但不得修改既有预期迎合实现。
- 样例固定包含 before/after 文件、人工标注的 kind/op/证据位置/是否顺序敏感/意图分组。先冻结预期，再实现规则；增加新行为时追加样例，不能为迎合实现修改旧标注。
- 正确识别率 = 正确匹配的人工标注变更数 / 人工标注变更总数，聚类前计算，目标 ≥80%。同一真实变化重复报多次不能重复计分，多出的条目计误报。
- 噪声比 = 主结论中的纯格式/已证实无语义影响的重排条目数 / 主结论条目总数，目标 ≤10%；总数为 0 时记 0，并单独检查漏报。纯格式样例不得产生肯定的语义变更结论。
- 误报数/类型单独报告。否定词、流程顺序与示例误分类作为必须通过的回归样例，不能用全局 80% 平均值掩盖这些已知关键错误。
- 保存样例来源与脱敏方式；不得默认上传真实 Skill，不能为测试而引入外部模型。

### 5.2 交付证据

一键体验入口：`uv run --no-sync python scripts/check_experience.py`。覆盖真实服务/CLI 初始化、监听生成修订（不调用手动 snapshot）、同内容五次保存不增加 Revision/Op、命名锚点不移动，以及终止服务后修改/重启补获与历史保留；新增恢复预览后取消、确认恢复、重复计划幂等、undo→undo，共 8 项。每次生成独立测试 Skill 和数据根，记录逐项 passed/failed/not_run 到 `dist/experience-check/run-*/result.json`，保留 CLI 和服务日志；失败非零退出，不把后续未运行项算通过。对应 AC-01/04/05/08/15/18 的部分行为，不替代完整 AC 或安装/界面验收；恢复中途强杀与路径冲突由 pytest 单独覆盖；进程终止不等同 Ctrl+C 优雅退出。

每个实现任务只选相关 AC，不要求每次跑完整套件。报告：关联需求/AC、运行命令、结果、未运行原因、文档更新及剩余待决项。存储/事务变更须测失败路径；算法变更须测无缓存重算；接口变更须测真实消费模型，不能只测自己构造的字典。

性能记录机器/系统、存储介质、文件数/字节数、算法与配置、缓存条件；至少给出 30 次重复的 p50/p95，目标按 p95 核对。运行受环境限制时标未验证，不以减少样例规模、禁用解析器或使用热缓存冒充目标通过。Python 3.11+ 的兼容性与 Windows/macOS/Linux 三平台分别给证据，未执行的平台不得宣称已验证。

### 5.3 Codex 中的人工行为验收

Codex 行为验收是外部人工流程，不属于 AC-01～20 的静态版本内核验收，也不填充规范报告的 `behavior` 字段。操作步骤与记录格式以 [Codex Skill 版本测试指南](./Codex%20Skill%20版本测试指南.md) 为准，并遵守以下证据边界：

- 每个被测版本由明确锚点或 Revision 标识；恢复后使用新的 Codex 任务，避免旧上下文污染。
- 不同版本使用相同模型设置、权限、项目路径、输入与判定标准；至少包含显式、隐式和负向触发用例。
- 测试结果单独保存在 Skill 目录之外，不写入规范 DiffReport，不将人工通过冒充 M-13 已接入。
- 只复制项目文件只能交付当前内容，不能作为历史、锚点或对象库已迁移的证据；跨机器历史导入尚未实现。
